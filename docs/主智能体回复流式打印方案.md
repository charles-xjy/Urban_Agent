# 主智能体回复流式打印方案

> 目标：让主智能体（非 researcher `internal` 卡片）的回复以约 5-10 字/秒的可见速率逐字打印到前端
> 分析日期：2026-07-28
> 行号基于当前代码状态，修改后可能漂移

## 一、现状分析（为什么现在是一整段蹦出来）

后端主回复有两个产出点，**都用 `.ainvoke()`（非流式，整段返回）**：

- `router_node`（`frontend/graph.py:181`）- chat / clarify 的短回复，`max_tokens=256`
  - chat 分支：`graph.py:193-201`，直接把 `reply` 包成 `AIMessage` 返回
  - clarify 分支：`graph.py:214-222`，把 `question` 包成 `AIMessage` 返回
- `web_reporter_node`（`frontend/graph.py:775`）- 最终分析报告，`max_tokens=8192`

前端 `streamMode: ["values"]`（`thread/index.tsx:359、364`）只在**每个节点跑完后**推送一次完整 state，所以主回复是节点结束那一瞬间整条出现的。

渲染入口在 `messages/ai.tsx:478-482`：

```tsx
{mainContent.length > 0 && (
  <div className="py-1">
    <MarkdownText>{mainContent}</MarkdownText>   // ← 整段一次性渲染
  </div>
)}
```

`MarkdownText` 是 `memo` 的（`markdown-text.tsx:354`），传入的字符串不变就不重渲染。

## 二、结论：改前端，不改后端

**核心改动在前端，不需要动后端。**

理由：你要的是「5-10 字/秒」这种**可控的慢速可见速率**，而 LLM 真实 token 流式速率由模型决定（vLLM 通常远快于此），没法精准压到 5-10 字/秒。所以正确做法是**前端打字机效果**：拿到完整文本后，按固定速率逐字 reveal。

把 LLM 真流式接到前端也没有意义——vLLM 吐 token 的速率根本不是 5-10 字/秒，要么太快（失去逐字观感），要么需要在前端再加速/限速。等于多此一举。

## 四、`useTypewriter` hook 设计

```ts
// use-typewriter.ts
import { useEffect, useRef, useState } from "react";

/**
 * @param text 完整文本
 * @param cps 每秒字符数（characters per second）
 * @param enabled 是否启用打字机；false 时直接返回全文
 */
export function useTypewriter(text: string, cps: number, enabled: boolean) {
  const [displayed, setDisplayed] = useState(enabled ? "" : text);
  const rafRef = useRef<number>();
  // 文本变化（新消息到达）时重置为 0
  useEffect(() => {
    if (!enabled) {
      setDisplayed(text);
      return;
    }
    setDisplayed("");
    // 每 1000/cps ms 推进若干字符
    const intervalMs = Math.max(16, 1000 / cps);
    const charsPerTick = Math.max(1, Math.round(cps * intervalMs / 1000));
    let i = 0;
    const id = setInterval(() => {
      i += charsPerTick;
      if (i >= text.length) {
        setDisplayed(text);
        clearInterval(id);
      } else {
        setDisplayed(text.slice(0, i));
      }
    }, intervalMs);
    return () => clearInterval(id);
  }, [text, cps, enabled]);
  return displayed;
}
```

关键点：
- 文本变化（新消息）时重置进度
- `enabled=false` 时直接返回全文，用于已展开过的历史消息
- 追平后 `clearInterval` 停表，避免泄漏

## 五、何时启用打字机（第 3 项设计点）

打字机只该对「本次会话新到达的回复」生效，不该在刷新 / 切线程后把历史消息重新逐字打一遍。

做法：在 `AssistantMessage` 内用 `useRef<Set<messageId>>` 记「已展开过」的 id：
- 首次见到某消息 → 逐字打，追平后标记
- 已标记 → 直接显示全文
- 刷新页面（会话重置、Set 清空）→ 历史消息按全文显示，不重打

## 六、关键坑：长报告会非常慢 ⚠️

按 7 字/秒算：

- router 短回复（~100-300 字）→ 15-45 秒，体验正好
- **reporter 报告（最长 8192 token，可能上千-数千字）→ 几分钟到十几分钟**，用户会等到崩溃

所以「5-10 字/秒」只适合短回复。长报告需要策略。

## 七、长报告策略（三选一）

### 方案 1：只对短回复打字机，长报告直接显示（最简单）
- 只对 router 的 chat / clarify 短回复打字机
- reporter 报告直接全文显示
- **区分方式**：报告消息通常 `state.report` 非空 / 来自 `web_reporter` 节点，可在消息 metadata 或长度上判断
- 优点：最省心，体验自然
- 缺点：长报告失去逐字观感

### 方案 2：自适应速率
- 文本越长速率越快（比如 >500 字提速到 30-50 字/秒）
- 短文才用 5-10 字/秒
- 优点：所有回复都有逐字观感
- 缺点：长报告速率仍需手动调参，观感不如方案 1 自然

### 方案 3：打字机 + 点击跳过
- 正常逐字打，但允许点一下「显示全部」立即展开
- 长报告也能用，用户不耐烦就点掉
- 优点：长报告也能用，给用户控制权
- 缺点：需要额外 UI

### 推荐：方案 1 + 方案 3 组合
- 短回复（router）→ 打字机逐字打（5-10 字/秒）
- 长报告（reporter）→ 直接全文显示
- 短回复打字机过程中 → 提供「点击展开全部」可跳过
- 最省心，体验最自然

### 8.3 判断「是否为 reporter 报告」

几种可选判断：
- **按消息 metadata 的节点名**：`thread.getMessagesMetadata(message)?.firstSeenState?.parent_checkpoint` 之类，看是否来自 `web_reporter` 节点。需要确认 SDK 暴露的字段。
- **按长度阈值**：`mainContent.length > 500` 视为报告，直接显示。简单粗暴，但短报告会误判。
- **按 `state.report`**：若该消息内容等于当前 `stream.values.report`，则视为报告。

推荐先用**长度阈值（>500 字）**作为 v1，简单可靠，后续再按节点名细化。

### 8.4 边界处理

- `isLoading` 期间用户切换消息或发新消息 → 打字机应立即停表、显示全文（`useTypewriter` 的 cleanup 会处理）
- 打字机进行中又来了新 token → 实际不会发生（当前是非流式，文本是一次性到达），但 hook 的 `text` 依赖变化时会重置进度，安全
- researcher 的 `internal` 卡片（`msgName === "internal"`）走的是 `AgentOutputCard` 分支（`ai.tsx:417`），**不经过 `mainContent` 渲染**，所以天然不受影响，无需特殊处理

# 最终报告流式打印方案

> 目标：让 `web_reporter` 节点生成的最终分析报告**边生成边显示**，而不是等整篇 8192-token 输出完后才一次性出现。
> 范围：仅最终报告。router chat/clarify 等短回复保持现状不动。
> 确定日期：2026-07-29
> 行号基于当前代码状态，修改后可能漂移。

## 一、问题

`web_reporter_node`（`frontend/graph.py:778`）用 `.ainvoke()` 一次性拿完整报告：

```python
# frontend/graph.py:790-807
resp = await _llm(max_tokens=8192).ainvoke([
    SystemMessage(content=_REPORTER_SYSTEM),
    HumanMessage(content=(...)),
])
report = resp.content
report = replace_report_sources(report, merged.sources)
return {"report": report, "messages": [AIMessage(content=report)]}
```

前端 `streamMode: ["values"]`（`thread/index.tsx:382/399/422`）只在节点跑完后推一次完整 state。于是用户在 reporter 生成的整段时间里只看到 loading，整篇报告在节点结束那一瞬间整条出现（渲染入口 `messages/ai.tsx:579-582`）。

`max_tokens=8192` 的中文报告容易到几千字，这段"无反馈等待"是当前最差的体验点。要让报告流式打印，把这段等待换成逐 token 显示即可。

## 二、方案：复用已有的 custom-event 流式管道

本项目**已经有一套验证可用的流式管道**，给 researcher 节点用着：

- 后端 `get_stream_writer()`（`graph.py:30` 已 import，`graph.py:557` 已使用）拿到 writer，`_emit()`（`graph.py:561-593`）把进度写成 custom event
- 前端 `useStream` 的 `onCustomEvent`（`providers/Stream.tsx:191-255`）接住 `research_progress` 事件，聚合到本地 state，驱动 `AgentOutputCard` 实时更新

给 reporter 接上**同一个机制**，"只让最后的报告流式"天然成立：只有 reporter 节点会发 `report_chunk` 事件，其他节点照旧 `ainvoke`。不需要改全局 `streamMode`，不影响 router / parse / planner / researcher。

### 为什么走 custom event 而不是 LangGraph `messages` mode

- `messages` mode 是全局开关，一开所有 AI 消息都走流式 token，会波及 router 短回复、researcher 内部 LLM 流（researcher 还专门用 `TAG_NOSTREAM` 隔离内部流，见 `graph.py:635`），改造面和副作用都大。
- custom event 是点对点的：只有显式 `writer(...)` 的节点会外露数据。对"只流式最终报告"这个诉求，它最贴合、改动面最小。

## 三、后端改动（仅 `web_reporter_node`）

`ainvoke` 换成 `astream` 迭代，每个 chunk 通过 writer 推给前端：

```python
# web_reporter_node 内
report = ""
try:
    writer = get_stream_writer()
except Exception:
    writer = None

async for chunk in _llm(max_tokens=8192).astream([
    SystemMessage(content=_REPORTER_SYSTEM),
    HumanMessage(content=(...)),
]):
    delta = chunk.content or ""
    if not delta:
        continue
    report += delta
    if writer is not None:
        try:
            writer({"type": "report_chunk", "delta": delta})
        except Exception:
            pass  # 流式事件失败不影响报告生成

report = replace_report_sources(report, merged.sources)   # 后处理照常
if writer is not None:
    try:
        writer({"type": "report_done"})
    except Exception:
        pass

return {"report": report, "messages": [AIMessage(content=report)]}
```

要点：

- **`ChatOpenAI.astream()` 总是流式**，不需要给 `_llm` 加 `streaming=True`，因此共享 `_llm` 的其他节点不受影响。
- reporter 的流是**要外露**的，所以**不加** `TAG_NOSTREAM`（与 researcher 内部流相反）。
- 节点末尾仍 return 最终版 report，`thread.messages` 照常得到完整消息——历史报告、刷新页面都走 message 的完整内容，**不存在打字机方案那种"刷新后重打"的持久化问题**。
- `findings` 为空时的兜底分支（`graph.py:780-785`）无需流式，保持原样直接返回。

## 四、前端改动

### 4.1 `providers/Stream.tsx`

- `CustomEventType` 增加 `ReportChunkEvent` / `ReportDoneEvent`（当前为 `UIMessage | RemoveUIMessage | ResearchProgressEvent`，`Stream.tsx:93`）。
- `StreamSession` 增加 `streamingReport` state（`string`，累积 delta）。
- `onCustomEvent`（`Stream.tsx:191`）新增分支：
  - `report_chunk`：把 `delta` 追加到 `streamingReport`。
  - `report_done`：清空 `streamingReport`（最终完整文本由后续 `values` 推送的 message 接管）。
- 通过 context 暴露 `streamingReport`。

为避免每个 token 触发一次 setState + markdown re-parse（LLM 速率 50-100 字/秒），前端做 **throttle**：用 ref 累积 delta，每 60-80ms flush 一次到 state（`requestAnimationFrame` 或 `setInterval` 均可）。这比"逐字 setState"高效得多。

### 4.2 `components/thread/messages/ai.tsx`

`RegularAssistantMessage`（`ai.tsx:521`）渲染入口（`ai.tsx:579-582`）改为：

```tsx
const { streamingReport } = useStreamContext();
const isStreamingReport =
  isLastMessage && streamingReport.length > 0 && isLoading;

// 流式期间显示累积文本；结束后显示完整 mainContent
const renderText = isStreamingReport ? streamingReport : mainContent;

{renderText.length > 0 && (
  <div className="py-1">
    <MarkdownText>{renderText}</MarkdownText>
  </div>
)}
```

- 流式期间用 `streamingReport`（正在生成中的正文），结束后切回 `mainContent`（节点返回的最终消息）。
- 判据用 `isLastMessage && isLoading`：节点跑完、`values` 推送最终 message 后 `streamingReport` 已被 `report_done` 清空，自然回落到 `mainContent`。
- research 卡片走 `InternalAssistantMessage`（`ai.tsx:515-516`），不经过此分支，不受影响。

## 五、真实难点：`replace_report_sources` 后处理

`replace_report_sources`（`core/source_merge.py:209`）做的是：扫描全文 `[n]` 引用 → 只保留被引用的来源 → **把编号压缩重排为 1..N 连续序列** → 重建 `## 来源` 区段。它**必须等完整文本**，无法增量做。

后果：流式期间用户看到的是 LLM 原始 token（原始编号 + 模型自己写的来源区段），节点结束后一瞬替换为规整版（编号可能变、来源区段重写）。这是路径无关的固有限制——无论用 custom event 还是 `messages` mode 都一样。

缓解方式（二选一）：

- **接受跳变**：正文通常变化极小（只是 `[n]` 改号），`## 来源` 区段在 `report_done` 后由最终 message 一次性替换，视觉上是一次收尾整理。
- **来源区段留到最后**：流式只推正文（在 writer 里过滤掉 `## 来源` 之后的 delta），来源区段等 `report_done` / 最终 message 补上。避免来源列表跳变，正文 `[n]` 改号仍会变但更不明显。

推荐前者：实现简单，且正文跳变通常用户感知不到。若实测来源区段跳变明显，再切后者。

## 六、不做的事

| 不做 | 原因 |
|------|------|
| 改全局 `streamMode` 加 `messages` | 副作用波及所有 AI 消息，与"只流式报告"诉求不符 |
| 给 router 短回复上打字机 | 短回复本来就快，无卡顿问题；保持现状 |
| 任何前端逐字限速（打字机） | 后端流式本身就是小 chunk 增量，逐 token 显示已经不卡，无需再压到 15 字/秒；限速反而凭空增加感知延迟 |
| 给 `_llm` 加 `streaming=True` | `astream()` 已支持流式，改动会波及共享 `_llm` 的其他节点 |

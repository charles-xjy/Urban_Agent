# 调试笔记：Maximum update depth exceeded（流式报告阶段）

> 报错全文：`Maximum update depth exceeded. This can happen when a component repeatedly calls setState inside componentWillUpdate or componentDidUpdate.`

---

## 一、报错含义

React 检测到**同一渲染周期内连续 setState 超过 50 次**而抛出，本质是某个组件陷入了
`setState → 重渲染 → 又 setState → 又重渲染 …` 的同步死循环。React 强行打断以防止页面卡死。

> 注意：单纯的"渲染慢/卡顿"≠ 这个报错。它一定是**有 state 在被反复写**，不是单纯计算量大。

---

## 二、流式报告这条链我已读过并排除的部分

后端流式实现（`frontend/graph.py:803` `web_reporter_node`）：

- 流式过程中**只发 custom event**（`report_chunk` / `report_done`，见 `graph.py:837`、`:846`）
- **最后才更新一次 graph state**（`return {"report": ..., "messages": [AIMessage(...)]}`，`:850`）
- 也就是说流式期间 `useStream` 的 `messages` / `values` 是稳定的，不会每个 chunk 触发 state 变更

前端 RAF 缓冲（`providers/Stream.tsx:191-218`）：

- `appendReportDelta`（`:200`）：只往 `reportBufRef.current`（ref，不触发渲染）追加，再 `requestAnimationFrame(flushReport)`，且用 `reportRafRef` 做了防重入 → **每帧最多一次 setState**
- `flushReport`（`:195`）：`setStreamingReport(reportBufRef.current)` → 单次 setState
- `resetReport`（`:207`）：`report_done` 时清空，无循环风险

`MarkdownText`（`markdown-text.tsx`）：

- `defaultComponents` 在**模块顶层定义**（`:78`），不是组件内每次新建 → 对象引用稳定，✓
- `MarkdownTextImpl` 已用 `memo` 包裹（`:398`），子组件 props 浅比较 → 仅在 `children`（报告文本）真正变化时重渲染

`ai.tsx` 渲染入口（`:579-589`）：

## 三、我的猜测（按可能性排序）

### 猜测 A（最可能）：报告中的 KaTeX / 代码块在部分 Markdown 上反复重解析

流式时 `streamingReport` 每帧增长，`MarkdownText` 每帧重渲染，`ReactMarkdown` 配了
`remarkGfm` + `remarkMath` + `rehypeKatex`（`markdown-text.tsx:350-353`）。每帧都对**整段不断增长的报告**做一次完整 AST 解析。

问题点：

- 报告写到一半时，`$$...$$` / `$...$` 数学块、```` ```代码块 ```` 经常是**残缺**的
- `rehype-katex` 对残缺/非法数学块的处理，可能让某个内部子组件在 `useState` 上反复 churn
- `SyntaxHighlighter`（`syntax-highlighter.tsx`）用的是 `PrismAsyncLight`（异步加载语言定义，`:1`）。报告里一旦出现代码块，`react-syntax-highlighter` 会**异步 import 语言模块**，这个异步注册流程可能触发额外渲染周期

> 这条不是严格意义的"同步死循环"，但 `PrismAsyncLight` 异步加载 + 每帧重解析 + 残缺 AST 的组合，最容易表现为 update depth 爆炸。

**怎么验证：** 临时把 `ai.tsx:581` 那段改成 `const renderText = mainContent;`
（关掉实时流式，等报告整段生成完再显示）。若报错消失 → 锁定在这条渲染链。

### 猜测 B：`onCustomEvent` 闭包每次新引用，导致 useStream 反复重订阅

`Stream.tsx:230` 的 `onCustomEvent` 是**内联函数**，组件每次渲染都是新引用。如果
`@langchain/langgraph-sdk` 的 `useStream` 内部把它放进依赖数组（而非用 ref 缓存），
就会：渲染 → 新闭包 → 重订阅 → 触发回调 → setState → 渲染 … 死循环。

> 但 SDK 一般用 ref 存 handler，所以这条概率中等偏低。仍值得一并查。

**怎么验证：** 把 `onCustomEvent` 改成 `useEvent`/`useCallback` + ref 稳定引用，看是否消失。

### 猜测 C：researchProgress 对象引用 churn（流式期间仍有 researcher 消息残留）

`thread/index.tsx:612` 用 `stream.researchProgress ?? {}`——**当 `researchProgress` 为空时，每次渲染传一个新 `{}`**。`ResearchProgressList` 内部 `Object.values(progress)`（`:104`）虽不触发 effect，但若有下游把 `progress` 进了 effect 依赖，空对象每次新引用就会循环。

- `Stream.tsx:320` 的 effect 依赖 `streamMessages`，流式期间若仍有 researcher 工具消息在抵达，`getPersistedAgentExecutionIds` 反复非空 → 反复 `setResearchProgress` → 对象引用变 → 下游重渲染

> 这条与"最终报告"场景关联较弱（报告阶段 researcher 应已结束），但 `?? {}` 这个新引用写法本身是个隐患，值得顺手修掉（用模块级常量 `EMPTY = {}`）。
